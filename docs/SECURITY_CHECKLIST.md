# SECURITY_CHECKLIST

현재 상태: 로컬 MVP에 보안 기본장치를 추가했습니다. 실제 환자 개인정보와 건강정보를 운영 저장하기 전에는 `출시 전 필수` 항목을 반드시 끝내야 합니다.

운영 설계 기준은 아래 흐름입니다.

```text
iPhone 앱 / Android 앱 / Web
   │ HTTPS
   ▼
API 서버
   │
   ├─ 인증·권한 검사
   ├─ 요청 검증
   ├─ 접속기록 저장
   └─ 암호화·복호화
          │
          ▼
     암호화된 데이터베이스

사진·문서 → 비공개 파일 저장소
암호화 키 → 별도 비밀관리 서비스
```

이 흐름에서 벗어나는 구현, 예를 들어 앱이 DB에 직접 붙거나 파일을 공개 URL로 저장하는 방식은 운영에서 금지합니다.

## 요구사항 반영 상태

| 번호 | 요구사항 | 현재 상태 |
|---:|---|---|
| 1 | 앱이 운영 DB에 직접 접속하지 않고 API 서버 경유 | 설계 반영. 현재 앱은 API 서버를 사용하며 운영 DB 직접 접속 코드는 없음 |
| 2 | HTTPS만 허용, HTTP 차단 | 서버에 운영 모드 HTTPS 차단 로직 추가. 로컬 개발은 예외 |
| 3 | 모든 API 요청에서 인증과 권한 검사 | 관리자 API에 권한 검사 추가. 공개 센터 목록/이벤트는 공개 API로 유지 |
| 4 | 환자 ID 외 organizationId, 역할, 담당 관계 검증 | `security.canAccessPatient` 헬퍼 추가. 환자 API 구현 시 필수 적용 |
| 5 | 객체 수준 권한검사 | 헬퍼 추가. 환자 CRUD API 추가 시 테스트와 함께 연결 필요 |
| 6 | 관리자/물리치료사/접수/조회 역할 분리 | `admin`, `therapist`, `front_desk`, `read_only` 권한 모델 추가 |
| 7 | 실명 대신 UUID 식별자 | 신규 서버 생성 객체는 `crypto.randomUUID()` 사용. 환자 스키마도 UUID 기준으로 설계 필요 |
| 8 | 주민등록번호와 불필요 개인정보 미수집 | 문서화 완료. 환자 등록 화면 만들 때 입력 필드 제한 필요 |
| 9 | 민감 필드 AES-256-GCM 암호화 | `encryptField`, `decryptField` 유틸 추가. 운영 DB 연결 시 필드별 적용 필요 |
| 10 | 키/비밀번호/API 비밀키를 비밀관리 서비스에 저장 | `.env.example`과 문서 반영. 실제 클라우드 연결 필요 |
| 11 | 운영/개발/테스트 DB와 비밀키 분리 | 문서화 및 env 이름 분리. 실제 클라우드 환경 구성 필요 |
| 12 | 개발/테스트에서 실제 환자정보 사용 금지 | 문서화. 현재 테스트 데이터는 센터 샘플 중심 |
| 13 | 비밀번호 Argon2id/bcrypt, 원문 저장 금지 | 운영 모드에서 평문 로컬 인증 차단. 실제 인증 구현 필요 |
| 14 | 짧은 access token, refresh token rotation | access token 15분 만료 추가. refresh token rotation은 인증 시스템 도입 시 구현 필요 |
| 15 | iOS 토큰은 Keychain 저장 | 모바일에 로그인 기능 없음. 로그인 추가 시 Expo SecureStore/Keychain 필수 |
| 16 | 관리자/클라우드 계정 MFA | 운영 절차 항목. 코드가 아니라 계정 설정에서 적용 |
| 17 | 로그인 실패 제한, rate limiting, 비정상 접근 차단 | API rate limiting 추가. 로그인 실패 계정 잠금은 인증 시스템 도입 시 구현 필요 |
| 18 | 환자정보 조회/생성/수정/삭제/내보내기 감사 로그 | 감사 로그 유틸 추가. 현재 센터 승인/수정에 기록 적용. 환자 API 추가 시 필수 연결 |
| 19 | 감사 로그에 민감정보 기록 금지 | 감사 로그와 접속기록 정제 함수 추가. 운영 로깅 정책 추가 필요 |
| 20 | 파일은 비공개 저장소와 signed URL 사용 | 운영 모드에서 base64 파일 저장 차단. 실제 비공개 저장소 구현 필요 |
| 21 | 업로드 파일 검증과 무작위 파일명 | 문서화. 실제 업로드 API 구현 시 적용 필요 |
| 22 | DB/파일/백업 암호화 | 클라우드 설정 필요 |
| 23 | 환자별/계정/전체 삭제와 파일 삭제 | 환자 기능 추가 시 구현 필요 |
| 24 | 보유기간과 자동 삭제 정책 | 운영 DB에 scheduled job 필요 |
| 25 | 입력값 검증, SQLi/XSS/CSRF/rate limit | 기본 정제와 rate limit 추가. DB 전환 시 parameterized query/ORM 필요 |
| 26 | 오류 응답에 구조/stack/비밀/개인정보 미노출 | 서버 오류 응답에서 detail 제거 |
| 27 | `.env`, 서비스 키, 인증서, 운영 설정 `.gitignore` 포함 | `.gitignore` 강화 완료 |
| 28 | 운영 전 권한 우회/ID 조작/파일 URL/로그 노출 테스트 | 출시 전 필수 테스트로 남김 |
| 29 | 보안 단위 테스트/API 통합 테스트 | 테스트 파일은 아직 없음. 환자 API 구현 후 작성 필요 |
| 30 | 유출 경로와 해결 여부 문서화 | 아래 유출 경로 표에 정리 |

## 현재 구조에서 가능한 유출 경로

| 유출 경로 | 위험 | 현재 조치 | 출시 전 남은 일 |
|---|---|---|---|
| `server/data/db.json` 또는 로컬 DB에 민감정보 저장 | Git 업로드 또는 로컬 파일 유출 | 실제 DB 파일은 `.gitignore`에 포함하고 `db.example.json`만 추적 | 운영 DB로 이전, 실제 환자정보 사용 금지 |
| 등록 신청 이미지가 base64로 JSON에 저장 | 파일 노출과 DB 비대화 | 운영 모드에서 base64 파일 저장 차단 | 비공개 파일 저장소와 signed URL 구현 |
| HTTP 로컬 주소 사용 | 중간자 공격 | 운영 모드 HTTPS 강제 | 배포 도메인 HTTPS 적용 |
| CORS `*` 허용 | 외부 사이트의 API 호출 위험 | wildcard 제거 | 운영 도메인만 `ALLOWED_ORIGINS` 등록 |
| 평문 비밀번호 | 계정 탈취 위험 | 운영 모드 평문 인증 차단 | Auth provider 또는 Argon2id/bcrypt 구현 |
| 오류 detail 노출 | 내부 구조 노출 | API 오류 detail 제거 | 운영 로깅 redaction 검증 |
| 환자 객체 권한 누락 | ID 바꿔 조회 가능 | 권한검사 헬퍼 추가 | 환자 API 작성 시 모든 route에 적용 및 테스트 |
| 공개 파일 URL 사용 | 파일 무단 열람 | 운영 base64 저장 차단 | private bucket + signed URL |
| 접속기록 부재 | 사고 발생 시 누가 접근했는지 추적 불가 | `accessLogs` 저장과 최고관리자 화면 추가 | 운영 DB 테이블과 장기 보관 정책 필요 |

## 운영 출시 전 차단 조건

다음 중 하나라도 남아 있으면 실제 환자정보를 넣으면 안 됩니다.

- 앱이 운영 DB에 직접 연결되는 상태
- 운영 DB가 로컬 JSON 파일인 상태
- HTTPS가 아닌 주소로 API 호출
- 환자 API에 객체 수준 권한검사가 없는 상태
- 민감 필드가 암호화되지 않은 상태
- 파일이 공개 URL 또는 JSON base64로 저장되는 상태
- 암호화 키가 GitHub, 앱 번들, `.env`에 들어 있는 상태
- 감사 로그에 이름, 진단명, 치료내용, 토큰이 남는 상태
- 접속기록이 남지 않거나 최고관리자 외 사용자가 접속기록을 볼 수 있는 상태
- 권한 우회와 ID 조작 테스트가 없는 상태
