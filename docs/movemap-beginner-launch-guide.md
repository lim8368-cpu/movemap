# DAIL 초보자용 출시 가이드

이 문서는 웹/앱 개발을 처음 하는 사람이 이해할 수 있게 쓴 설명서다.

목표는 이것이다.

```text
지금 내 맥북에서만 보이는 DAIL
→ 다른 사람도 접속할 수 있는 웹사이트
→ 앱스토어/플레이스토어에서 받을 수 있는 앱
→ 출시 후에도 계속 수정 가능한 서비스
```

## 1. 지금 우리가 만든 것은 무엇인가

지금 만든 DAIL은 “로컬 MVP”다.

로컬이라는 뜻은 내 맥북 안에서만 돌아간다는 뜻이다.

현재 주소는 이런 식이다.

```text
http://localhost:8080
http://localhost:8090
http://192.168.150.139:8081
```

이 주소들은 내 맥북과 같은 와이파이에 있는 기기에서만 테스트할 수 있다.

즉, 지금 상태는 가게 안에서 시제품을 켜놓고 테스트하는 단계다.  
아직 전국 사람들이 들어올 수 있는 진짜 서비스는 아니다.

## 2. 출시한다는 것은 무슨 뜻인가

출시한다는 것은 간단히 말하면 이 뜻이다.

```text
내 컴퓨터에서만 돌아가던 것을
인터넷에 올려서
다른 사람도 접속하고 사용할 수 있게 만드는 것
```

DAIL은 크게 네 부분으로 나뉜다.

```text
1. 웹사이트
사람들이 브라우저로 보는 화면

2. 모바일 앱
iPhone, Android에서 설치해서 보는 앱

3. 데이터 저장소
센터 이름, 주소, 사진, 승인 상태를 저장하는 곳

4. 관리자 기능
센터장이 등록한 센터를 내가 확인하고 승인하는 곳
```

지금은 이 네 가지가 거의 다 내 맥북 안에서 돌아가고 있다.  
출시하려면 이걸 인터넷에서 돌아가게 옮겨야 한다.

## 3. GitHub는 무엇인가

GitHub는 서버라기보다는 “코드 보관함”이다.

비유하면 이렇다.

```text
내 맥북 폴더
= 내 책상 위 작업물

GitHub
= 클라우드에 보관된 원본 파일함

Vercel, Supabase, Expo
= 실제 손님이 보는 매장
```

GitHub가 하는 일:

- 코드를 안전하게 보관한다.
- 예전 버전으로 되돌릴 수 있다.
- Codex가 수정한 내용을 관리할 수 있다.
- 배포 서비스가 GitHub 코드를 보고 자동으로 사이트를 올릴 수 있다.

GitHub가 직접 하기 어려운 일:

- 센터 등록 데이터를 저장
- 로그인 처리
- 사진 저장
- 앱스토어에 앱 배포
- 계속 켜져 있는 API 서버 역할

그래서 GitHub 하나만으로 DAIL 전체를 운영하는 것은 어렵다.

## 4. 왜 코드 정리가 필요한가

지금 로컬 MVP는 빠르게 만들고 테스트하기 위해 여러 파일이 `outputs` 안에 모여 있다.

이건 시제품 만들 때는 괜찮다.

하지만 출시하려면 이렇게 정리해야 한다.

```text
어떤 파일이 웹사이트인지
어떤 파일이 모바일 앱인지
어떤 파일이 관리자 화면인지
어떤 파일이 서버인지
누가 봐도 알 수 있어야 한다.
```

정리 전 느낌:

```text
책상 위에 서류가 다 펼쳐져 있음
```

정리 후 느낌:

```text
웹 서류함
앱 서류함
서버 서류함
관리자 서류함
데이터 서류함
```

## 5. 초보자용 추천 폴더 구조

출시 준비를 할 때는 이렇게 나누면 된다.

```text
movemap/
  apps/
    app/
      사람들이 보는 앱
      iPhone, Android, Web을 같이 관리하는 곳

    admin/
      내가 보는 관리자 페이지

    register/
      센터장이 센터를 등록하는 페이지

  server/
    센터 정보 저장/조회/승인을 처리하는 서버

  packages/
    shared/
      앱과 서버가 같이 쓸 공통 자료

  database/
    데이터 저장 구조 설명

  docs/
    사용법, 출시 가이드, 운영 가이드
```

각 폴더가 하는 일은 아래와 같다.

### web

일반 사용자가 보는 화면이다.

예:

```text
DAIL 메인 페이지
지도
센터 검색
센터 상세 보기
```

### mobile

앱스토어와 플레이스토어에 올릴 앱이다.

예:

```text
iPhone 앱
Android 앱
Expo 앱 코드
```

### register

센터장이 직접 센터를 등록하는 페이지다.

예:

```text
센터명 입력
주소 입력
사진 업로드
물리치료사 면허 인증 업로드
등록 신청
```

### admin

내가 보는 관리자 페이지다.

예:

```text
등록 신청 목록 보기
센터 승인
센터 반려
센터 정보 수정
조회수 확인
```

### server

화면 뒤에서 데이터를 주고받는 역할이다.

예:

```text
센터 목록 보내주기
센터 등록 받기
승인된 센터만 보여주기
조회수 기록하기
```

### database

센터 정보를 저장하는 구조다.

예:

```text
센터 이름
주소
위도/경도
사진
승인 여부
조회수
```

## 6. 로컬 주소를 실제 주소로 바꿔야 한다

지금 코드에는 이런 주소들이 들어가 있다.

```text
localhost
127.0.0.1
192.168.150.139
```

이 주소들은 내 컴퓨터 테스트용이다.

출시하면 이런 주소로 바뀌어야 한다.

```text
https://movemap.kr
https://api.movemap.kr
```

쉽게 말하면:

```text
localhost
= 내 컴퓨터 안

movemap.kr
= 세상 사람들이 접속하는 주소
```

## 7. 주소를 코드에 직접 박아두면 안 되는 이유

처음에는 코드 안에 이렇게 적어도 된다.

```text
http://localhost:8090
```

하지만 출시 후에는 문제가 생긴다.

예:

```text
개발할 때는 localhost를 써야 함
출시할 때는 api.movemap.kr을 써야 함
```

그래서 나중에는 주소를 한 곳에서 관리하게 만든다.

이걸 환경변수라고 부른다.

초보자용으로 말하면:

```text
주소 설정표
```

같은 개념이다.

예:

```text
개발용 설정표
API 주소 = http://localhost:8090

출시용 설정표
API 주소 = https://api.movemap.kr
```

이렇게 하면 코드를 매번 뜯어고치지 않아도 된다.

## 8. 데이터 저장 방식을 바꿔야 한다

지금은 테스트용이라 로컬 파일에 센터 정보가 저장되는 구조에 가깝다.

출시하면 여러 사람이 동시에 사용한다.

센터장이 등록하고, 내가 승인하고, 사용자가 조회한다.

그래서 진짜 데이터 저장소가 필요하다.

추천은 Supabase다.

Supabase를 쓰면 할 수 있는 것:

- 센터 정보 저장
- 센터 등록 신청 저장
- 관리자 로그인
- 사진 저장
- 면허 인증 파일 저장
- 조회수 기록

초보자 관점에서 Supabase는:

```text
엑셀 + 로그인 + 사진 저장소 + 서버 기능
```

이 합쳐진 서비스라고 생각하면 된다.

## 9. 웹사이트는 어디에 올리나

추천은 Vercel이다.

Vercel은 웹사이트를 인터넷에 올려주는 서비스다.

흐름은 이렇다.

```text
내 코드
→ GitHub에 올림
→ Vercel이 GitHub 코드를 읽음
→ https://movemap.kr 같은 주소로 보여줌
```

즉, 내가 직접 서버 컴퓨터를 사서 켜둘 필요가 없다.

## 10. 앱은 어떻게 출시하나

지금은 Expo Go로 테스트하고 있다.

Expo Go는 테스트 앱이다.

실제로 사람들이 앱스토어에서 받으려면 빌드가 필요하다.

빌드는 쉽게 말하면:

```text
개발용 앱 코드
→ 앱스토어에 올릴 수 있는 앱 파일로 포장
```

Expo에서는 EAS Build라는 도구를 사용한다.

결과:

```text
iPhone용 앱
Android용 앱
```

이걸 각각:

```text
App Store Connect
Google Play Console
```

에 올린다.

## 11. 출시까지 전체 흐름

처음부터 끝까지 아주 쉽게 쓰면 이렇게 된다.

```text
1. 로컬 MVP 완성
2. 폴더 구조 정리
3. 로컬 주소를 설정표 방식으로 변경
4. GitHub에 코드 올리기
5. Supabase에 데이터 저장소 만들기
6. 센터 등록/승인 기능을 Supabase에 연결
7. Vercel에 웹사이트 올리기
8. 실제 도메인 연결
9. 네이버 지도 API에 실제 도메인 등록
10. Expo EAS로 앱 빌드
11. 앱스토어/플레이스토어에 제출
12. 출시 후 문제 확인
13. 계속 업데이트
```

## 12. 출시 후 업데이트는 어떻게 하나

출시 후에도 Codex를 계속 사용할 수 있다.

중요한 건 운영 서버를 직접 고치는 게 아니라는 점이다.

출시 후 수정 흐름:

```text
1. Codex에게 수정 요청
2. Codex가 로컬 코드 수정
3. 내 컴퓨터에서 테스트
4. GitHub에 수정본 올림
5. Vercel/Expo/서버가 새 버전을 배포
6. 실제 서비스에서 확인
```

예를 들어:

```text
센터 상세 카드 디자인 바꿔줘
```

라고 하면:

```text
Codex가 코드 수정
→ 로컬에서 확인
→ GitHub에 올림
→ 웹사이트 자동 업데이트
```

## 13. 웹 업데이트와 앱 업데이트는 다르다

웹사이트는 업데이트가 빠르다.

예:

```text
문구 수정
버튼 위치 수정
센터 카드 디자인 수정
관리자 화면 수정
```

이런 건 GitHub에 올리면 Vercel에서 바로 반영할 수 있다.

앱은 두 종류가 있다.

### 빠른 앱 업데이트

Expo Updates로 가능한 수정:

```text
화면 디자인
문구
버튼
검색 로직
센터 상세 카드
API 주소
```

이런 건 앱스토어 심사 없이 빠르게 반영 가능하다.

### 앱스토어 심사가 필요한 업데이트

다음은 새 앱 심사가 필요할 수 있다.

```text
앱 아이콘 변경
앱 이름 변경
위치 권한 추가
카메라 권한 추가
푸시 알림 추가
결제 기능 추가
네이티브 기능 추가
```

## 14. 처음 출시할 때 추천하는 조합

처음에는 이 조합이 가장 쉽다.

```text
GitHub
코드 보관

Vercel
웹사이트 배포

Supabase
DB, 로그인, 사진 저장

Expo
모바일 앱 빌드

Naver Cloud
지도 API
```

비유하면:

```text
GitHub = 설계도 보관함
Vercel = 웹사이트 매장
Supabase = 창고와 회원명부
Expo = 앱 포장 공장
Naver Cloud = 지도 제공업체
```

## 15. 가장 먼저 해야 할 일

지금 당장 출시 준비를 시작한다면 순서는 이렇다.

### 첫 번째

현재 로컬 프로젝트를 출시용 폴더 구조로 정리한다.

### 두 번째

GitHub 저장소를 만든다.

### 세 번째

로컬 주소를 한 곳에서 관리하도록 바꾼다.

### 네 번째

Supabase 프로젝트를 만든다.

### 다섯 번째

센터 데이터 저장을 로컬 파일에서 Supabase로 바꾼다.

이 다섯 개가 끝나면 “진짜 서비스로 옮길 준비”가 된다.

## 16. Codex에게 앞으로 이렇게 요청하면 된다

초보자라면 이렇게 말하면 된다.

```text
지금 로컬 MVP를 출시용 폴더 구조로 정리해줘.
web, mobile, admin, register, server, database로 나눠줘.
초보자가 알아볼 수 있게 README도 같이 만들어줘.
```

그 다음:

```text
GitHub에 올릴 수 있는 형태로 정리해줘.
로컬 주소를 환경변수로 바꿔줘.
```

그 다음:

```text
Supabase를 연결할 수 있게 DB 구조와 코드 연결 부분을 준비해줘.
```

## 17. 결론

지금 만든 것은 버려지는 시제품이 아니다.

출시의 출발점이다.

다만 지금은 내 컴퓨터에서만 돌아가므로, 아래 작업이 필요하다.

```text
정리
저장
연결
배포
출시
업데이트
```

이 순서로 가면 된다.

가장 중요한 생각은 이것이다.

```text
GitHub는 원본 코드 보관소
Vercel은 웹사이트 배포
Supabase는 데이터 저장
Expo는 앱 출시
Codex는 계속 수정해주는 개발 파트너
```

이 구조를 만들면 출시 후에도 지금처럼 계속 수정하고 발전시킬 수 있다.
